## 第一轮：旧八项（针对 e52e762，已在 8ae2c45 修复并复核）

下列每条先写旧 head 上的复现与当时处置，再写修后 head 上的验证。旧实现上的假通过或误拒不得再写成产品承诺。

### 1. 缩进的 frontmatter 分隔符

旧 head 复现成立。依赖写在缩进的 `---` 之前、服务器声明写在其后时，旧实现退出码 0，矩阵只有工具满足，没有服务器行。当时处置为采纳：只有行首且整行正好为 `---` 才结束 frontmatter。

修后验证：同一形状现为退出码 1，矩阵保留服务器行，`search` 为缺失。现有测试 `tests/test_review_inputs.py::ReviewInputTests::test_indented_delimiter_does_not_drop_server_binding` 使用 `fixtures/snapshots/any-on-other.json`，断言退出码 1，标准错误含 `unsatisfied: search`，并且标准输出含 `docs`。没有假通过。

### 2. `--skill` 根路径是目录符号链接

旧 head 复现成立。有效目录链接会退出码 0 并显示满足；断链当时报成找不到目录；祖先段中的链接，以及先经过链接再用 `..` 返回的路径，也会被跟随。子目录链接、`SKILL.md` 链接和快照文件链接在旧实现里就会拒绝。当时处置为采纳：按参数原文每一段拒绝符号链接，退出码 2，不显示满足；不把进程怎样进入当前工作目录算进参数检查。

修后验证：有效目录链接、断链、祖先段链接、`symlink-skill/../real-skill` 这类经过链接再 `..` 的路径、快照路径链接，以及普通 skill 与目录链接的混合输入，均为退出码 2，标准输出不出现「满足」。对应测试包括 `test_skill_directory_symlink_is_refused`、`test_broken_skill_symlink_is_refused`、`test_symlink_ancestor_and_dotdot_are_refused`、`test_snapshot_through_directory_symlink_is_refused`、`test_real_skill_mixed_with_symlink_stays_exit_2`。断链的标准错误是「符号链接不允许」，不再是「找不到目录」。

### 3. 快照版本 `1.0` 和 `true`

旧 head 复现成立。两者都退出码 0，并给出与整数 1 相同的满足矩阵。原因是相等比较把这些值与 1 看成相同。当时处置为采纳：版本必须是 JSON 整数 1，布尔值和浮点都拒绝，退出码 2。

修后验证：把合法封装里的 `skill_deps_gate_snapshot` 分别改成 `1.0` 和 `true` 后，退出码均为 2，标准输出不出现「满足」。现有测试 `test_snapshot_version_must_be_int_one` 覆盖这两例。标准错误仍使用「不是样本封装」的说明模板，这是文案不精确，不是又把非法版本当成通过。

### 4. 嵌套不可读目录

旧 head 复现成立。非 root 环境下，合法 skill 旁边有权限为 0 的空目录时，旧实现退出码 0，只报告合法 skill。当时处置为采纳：扫描错误要回传，整轮退出码 2，已发现的行改为未判定。

修后验证：同一布局在非 root 下退出码 2，合法行为未判定，标准错误含「目录不可读」。现有测试 `test_nested_unreadable_directory_is_not_a_pass` 覆盖该行为；该测试在以 root 运行时会跳过，这一覆盖缺口见后文残留项。

### 5. 1,000,000 字节和 1 MiB

旧 head 复现成立。旧代码在超过 1,000,000 字节时拒绝，因此 1,000,001 字节会报过大，而 1 MiB 是 1,048,576 字节。这会误拒，不是依赖假通过。当时处置为采纳：上限改为明确常数 1,048,576 字节。

修后验证：用合法 frontmatter 把单个 `SKILL.md` 精确填到 1,000,000、1,000,001 和 1,048,576 字节时，退出码均为 0 且矩阵满足；1,048,577 字节退出码 2，标准错误含「SKILL.md过大」。现有测试 `test_size_limit_is_one_mebibyte` 对超过上限的一侧有断言，但对「低于 1 MiB 不被大小规则拒绝」的正面用例不完整，见后文残留项。

### 6. 扫描错误丢掉同根合法 skill

旧 head 复现成立。同一根里既有合法 skill 又有子目录符号链接时，旧实现退出码 2 且标准输出为空。当时处置为采纳保留已发现行：整轮仍是 2，这些行显示未判定，不显示满足，也不读取链接目标。

修后验证：指向根外真实目录的子目录链接、指向根内的子目录链接、以及扫描中遇到的 `SKILL.md` 文件链接，均为退出码 2，同根已发现的合法行保留为未判定。现有测试 `test_scan_error_keeps_discovered_skill_as_undecided` 与 `test_symlink_escape_is_refused` 覆盖「保留未判定、不跟随目标」这一侧。若同一根里还有依赖本身缺失的 skill，缺失行不会改成未判定，见后文残留项。

### 7. FIFO `SKILL.md`

旧 head 复现成立。对目录里名为 `SKILL.md` 的 FIFO 运行时，进程会挂起直到超时，标准输出和标准错误都为空。快照 FIFO 在旧实现里已会以退出码 2 拒绝。当时处置为采纳：`SKILL.md` 和快照都在读取前要求普通文件，退出码 2，不再打开 FIFO。

修后验证：对 skill FIFO 与快照 FIFO，均在短超时内以退出码 2 返回，标准错误含「不是普通文件」，不出现「满足」。现有测试 `test_fifo_skill_and_snapshot_do_not_hang` 覆盖这两例。

### 8. `license` 等顶层字段

旧 head 复现成立。带 `license: MIT` 且依赖本身满足的技能退出码 1，原因是未知字段。当时处置为部分采纳：允许但不解释 `license`、`compatibility`、`metadata`、`allowed-tools`；未知依赖组合仍然拒绝。这不是完整规范支持。

修后验证：单独出现 `license`，或同时出现上述四个字段，配合 `fixtures/snapshots/scan-ok.json` 时退出码 0，矩阵只出现依赖满足行。未知顶层字段（例如 `homepage`）和未知依赖组合（例如 `dependencies.tools.extra`）仍为退出码 1，标准错误以 `unsupported:` 开头。现有测试 `test_license_metadata_is_ignored_and_unknown_dependency_is_not` 覆盖白名单与未知依赖这一侧。

## 第二轮：补审十二项（针对 8ae2c45）

### 1. 声称可用 `link/../real-skill` 绕过祖先链接检查

模型判断：把该项定为阻断。认为 `supplied_path_has_symlink` 对 `..` 段处理不当，`link/../real-skill` 会把前面的链接段抵消，从而退出码 0 并显示满足。

研发实测：按报告给出的布局，以及 `real-skill/../link`、`link/../link/real-skill`、`target/../link/real-skill` 这些变体，退出码全部为 2，标准错误均为「符号链接不允许」，矩阵不出现「满足」。现有测试 `test_symlink_ancestor_and_dotdot_are_refused` 已覆盖 `symlink-skill/../real-skill` 这一形状。实现是按参数段逐段检查，链接段会在被 `..` 拼掉之前被抓住，后段若是链接也会被抓住。

处置：不采纳。这不是旧第 2 项的残留阻断，也不是修复引入的新绕过。

### 2. 声称检查符号链接时遇到操作系统错误会当成「无链接」

模型判断：定为必须修复。`is_symlink()` 在权限不足等情况下抛出错误时，实现返回「不是链接」，担心随后会跟随目标并给出满足。

研发实测：将链接所在父目录改为当前用户不可进入后，链接检查确实不再报「符号链接不允许」，整轮退出码仍为 2，标准错误是「目录不可读」，矩阵不出现「满足」。未能构造出后续存在性或可读性检查反而通过、从而读取链接目标并显示满足的布局。父目录权限恢复后，同一参数会正确报「符号链接不允许」。

处置：部分采纳为错误分类，不作为必须修复的阻断。输入仍被拒绝，只是标准错误类别与「符号链接不允许」不一致。本轮不新开实现，也不把这一条写成可以通过的漏洞。

### 3. 声称扫描错误轮次里「缺失」行未改成未判定，且标准错误仍有 `unsatisfied:`

模型判断：定为必须修复。认为整轮既是输入错误，缺失行也应改为未判定，并且不应再输出 `unsatisfied:`。

研发实测：在一个扫描根里同时放入依赖缺失的 skill、依赖满足的 skill，以及指向真实目录的子目录符号链接，然后运行 `python3 -m skill_deps_gate --skill <该根> --snapshot fixtures/snapshots/scan-ok.json`。退出码为 2。本来满足的行改为未判定；缺失行仍显示「缺失」；标准错误同时出现 `error:`（符号链接不允许）和 `unsatisfied:`。没有出现「满足」，也没有跟随该子目录链接去评估根外技能。

处置：现象成立，作为本轮保留的非阻断行为，须在 README 精确披露，不新开实现线。范围说明只要求把原本满足的行改成未判定，并允许标准错误以 `error:`、`unsatisfied:` 或 `unsupported:` 开头。这不会把输入错误轮次变成退出码 0，但容易被误读成依赖结论。详见后文残留项。

### 4. 声称扫描不可读目录时错误路径风格不一致

模型判断：定为必须修复。认为回传扫描错误时会泄露绝对路径，并与矩阵中的相对路径不一致。

研发实测：使用相对参数 `--skill root`（其中 `root/locked` 不可读，`root/ok` 为合法 skill）时，退出码 2，标准错误是 `error: root/locked: 目录不可读`，与矩阵里的相对路径一致。仅当调用者把 `--skill` 写成绝对路径时，错误消息里才会出现绝对路径，这是回显调用者给出的路径形式，不是实现另行泄露本机路径。

处置：不采纳为缺陷。

### 5. 声称带 `..` 的普通扫描根会使边界判断失准

模型判断：先写必须修复，后又在同一条意见里降为建议并承认部分情形符合文档。担心 `a/../b` 与解析后的根目录混用会导致异常退出或误拒。

研发实测：在普通目录布局下以 `--skill a/../b` 扫描，退出码 0，矩阵正常满足。若在该根内再放指向根内其他子目录的符号链接，退出码 2，合法行为未判定，标准错误为「符号链接不允许」，与「即便目标仍在根内也拒绝」的说明一致。没有出现未捕获异常，也没有把合法、无链接的 `a/../b` 误判为输入错误。

处置：不采纳为缺陷。

### 6. 声称非常规行尾的 `---` 会再次截断 frontmatter 并假通过

模型判断：定为建议修复。认为 `splitlines` 识别的行尾比实现剥离的行尾更宽，`---\x0c` 之类可能让服务器声明丢失，从而在绑定本应失败时退出码 0。

研发实测：按其样例、缩进变体、只用非常规行尾收尾、以及 Unicode 下一行分隔符等形状，全部退出码 2，标准错误为 frontmatter 解析失败，不出现「满足」。没有复现旧第 1 项那种丢掉服务器行后的假通过。

处置：不采纳为假通过。非常规行尾不会被当成合法分隔符，当前失败方向是输入错误，不是退出码 0。

### 7. 声称 `tools: null` 与 `dependencies: null` 退出码不一致

处置：采纳为分类不一致，作为本轮保留的非阻断行为，须在 README 披露，不新开实现线。详见后文残留项。

## 本轮保留、须在 README 精确披露的非阻断行为

这些是修后 head 上仍然存在的真实行为。本轮不新开实现线。它们不会把已经修好的假通过（缩进分隔符、根路径符号链接跟随、非法版本被接受、嵌套不可读被忽略、FIFO 挂起）再变回退出码 0，因此不作为本轮阻断，但必须写进面向使用者的说明，不能省略或写反。

### 1. 退出码 2 的轮次里仍可能出现「缺失」行和 `unsatisfied:`

现状：只要出现输入错误，整轮退出码就是 2，本来满足的行会改成未判定，不会显示满足。同一轮里若还有依赖本身缺失的 skill，这些行仍显示「缺失」，标准错误在 `error:` 之外还可以出现 `unsatisfied:`。用扫描根里同时放入缺失 skill、满足 skill 和指向真实目录的子目录链接，即可复现。

影响：按退出码判断时仍会把它当成输入错误。若只看矩阵里的「缺失」或只解析 `unsatisfied:`，可能误以为这是可以单独修复的依赖问题，而忽略同轮的输入错误。

为何本轮非阻断：没有假通过，也没有把输入错误降成退出码 0 或 1。范围说明已经写了「满足行改未判定」，但没有承诺缺失行也会改写，也没有禁止同轮出现 `unsatisfied:`。README 应写明：退出码 2 时，矩阵与标准错误不能当作依赖结论；不要写成「输入错误轮次只会看到 `error:` 和未判定」。

### 2. `null` 在不同声明层级上的退出码不一致

现状：`dependencies.tools` 为空或为 `null` 时退出码 1，标准错误是依赖声明为空、拒绝视为通过。`dependencies` 本身为 `null` 时退出码 2，标准错误是依赖声明格式不正确。两种都不会显示满足。

影响：把退出码 1 当成「依赖问题」、把退出码 2 当成「输入错误」的调用方，会把这两种同样无效的声明分到不同处理路径。

为何本轮非阻断：不是把空声明当成通过，只是分类不一致。README 应分别写明这两种输入的退出码，不要把它们说成同一种错误。

### 3. 扫描会忽略指向不存在目标的子项链接，以及非 `SKILL.md` 的文件链接

现状：扫描阶段的拒绝范围，产品说明写的是「子目录符号链接或 `SKILL.md` 符号链接」。在扫描根里放一个指向不存在目标的子项符号链接，或一个不叫 `SKILL.md` 的普通文件符号链接，实现不会拒绝，同根合法 skill 仍可退出码 0 并显示满足。指向真实目录的子目录链接，以及名为 `SKILL.md` 的文件链接（包括断链），仍会拒绝，整轮退出码 2，合法行保留为未判定。直接输入的 `--skill` 或 `--snapshot` 若自身是断链，仍会退出码 2。

影响：不能把扫描策略理解成「目录树里出现任何符号链接都退出 2」。这两类被忽略的链接不会被跟随去评估目标里的技能，因此不是旧第 2 项那种读取链接目标后的假通过；但目录里确实存在符号链接时，整轮仍可能显示通过。

为何本轮非阻断：与已修复的「参数根路径是目录链接却跟随并满足」不是同一类问题，现行范围说明也没有把扫描拒绝写成「任意符号链接」。README 必须按上面这条实际范围来写，不要夸大，也不要漏掉断链子项和普通文件链接会被忽略。

### 4. 重复的依赖声明会在矩阵里重复出现

为何本轮非阻断：产品说明未要求去重，判定结果与单次声明相同。README 可写明列表按声明重复展开，调用方若需要唯一名称应在声明里自行避免重复。
